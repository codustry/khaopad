 1.  SLIDE 1 — CASE STUDY
     Title:    Khao Pad — the website platform for Cloudflare
     Subtitle: 11 shipped milestones, one Cloudflare Worker,
               MIT-licensed.
================================================================

── PROBLEM ─────────────────────────────────

Every existing CMS forces a trade-off when you want to run
a content-heavy website on Cloudflare's free / near-free tier.

  • Supabase
      Great ecosystem, but $25/mo+ per project starts to hurt
      for small sites — and you still need a separate compute
      layer to serve pages.

  • Self-hosted Strapi (or Directus)
      Big footprint. Separate Node.js deployment. Not
      edge-native. Migrations feel enterprise-y even for a
      small marketing site.

  • Pages CMS / TinaCMS
      Lovely UI, git-backed content. Falls apart the moment
      you want real DB semantics: full-text search, comments,
      subscriber lists, form submissions, versioning.

  • Ghost / Wagtail / WordPress
      Mature but heavy. Opinionated about hosting. Not
      edge-deployable. Locale support is bolt-on, not a
      first-class citizen.

  • Build-your-own on Cloudflare
      Every team we know has started this from scratch.
      They stall at "which auth?", "how do I do i18n?",
      "why is my SEO empty?", and never ship the last 30%.

The Cloudflare stack (Workers + D1 + R2 + KV) is the cheapest,
fastest way to host a content site in 2026. But nothing
off-the-shelf makes the most of it — and everyone rebuilds
the same 30 primitives from scratch.


── SOLUTION ────────────────────────────────

Khao Pad. One open-source SvelteKit app deployed as one
Cloudflare Worker.

  Public site at  /
  Admin CMS at    /cms/*
  One repo. One host. Two surfaces. Sub-10ms reads worldwide.

Two conceptual layers, both shipped:

CONTENT LAYER (v1.0 – v1.5)
  – Articles + Pages, multilingual (English + Thai out of the
    box; more locales trivial to add). Shared slug per article.
  – Categories + Tags, with public blog filtering
    (/blog?category=… , ?tag=…).
  – Media library (R2-backed) with folders, drag-upload,
    alt text, and responsive srcset via Cloudflare Images.
  – Markdown editor: toolbar, split preview, ⌘B / ⌘I / ⌘K,
    autosave to localStorage with a recovery banner.
  – Scheduled publishing — set a future publishedAt and the
    public site 404s until that moment.
  – SQLite FTS5 full-text search over per-locale content,
    exposed on public /blog?q= and in-CMS list filter. Thai-
    friendly tokenizer (unicode61 remove_diacritics 2).
  – Per-article revision history: line diff, one-click
    restore, attribution to editor.
  – Audit log of every meaningful CMS action.
  – Token-based invitations for onboarding editors.

GROWTH ENGINE (v1.6 – v2.0)
  – SEO — per-page title/description/canonical, full Open
    Graph, Twitter Card, hreflang with x-default, sitemap
    index → per-locale sitemaps, per-environment robots.txt,
    RSS 2.0 feeds, Article + WebSite + SearchAction JSON-LD,
    slug redirects (301 old → new), soft SEO scoring hint.

  – Analytics — privacy-friendly D1 page-view counter
    (aggregated per date+path, no IP / no UA / no fingerprint).
    Gated on the visitor's cookie consent. Search insights,
    per-article 30-day sparkline. Optional Cloudflare Web
    Analytics beacon.

  – Performance & Trust — Cloudflare Images responsive srcset
    (falls back gracefully). Edge cache-control hook. Branded
    404 / 500 with search. /api/health returns per-binding
    reachability + latency.

  – Engagement & Growth — Public forms with honeypot + IP-hash
    rate limit. Newsletter with double-opt-in (Resend
    integration optional) and one-click unsubscribe. Comments
    with dual-toggle moderation and reply-via-email. HMAC-
    signed webhooks with auto-retry. Public REST API with
    bearer-token auth and per-key scopes.

 2.  SLIDE 2 — TECHNICAL ARCHITECTURE
     Title:    One Repo. Five Pillars. Edge-Native.
     Subtitle: How Khao Pad is built (deep dive)
================================================================

── RUNTIME ─────────────────────────────────

Single SvelteKit 2 + Svelte 5 app deployed as one Cloudflare
Worker. Path-based surface routing in hooks.server.ts:

  /cms/*   → admin (auth-gated, Cache-Control: no-store)
  /api/*   → API endpoints
  /*       → public site with per-locale prefix (/en, /th)

Handle hook chain (executed in order for every request):

  surfaceHook              — classifies the request surface
  bindingsHook             — injects platform.env D1/R2/KV
  configurationGuardHook   — renders a 503 config screen when
                             bindings are missing (local dev
                             without wrangler, for example)
  paraglideLocaleHook      — resolves locale via URL → cookie
                             → default
  authHook                 — attaches Better Auth session
  cacheHook                — sets Cache-Control per route

Deploys as a single Worker. No separate server processes. No
per-region replicas to configure. No CDN to buy separately.
Cloudflare's edge is the CDN.


── STORAGE — THREE CLOUDFLARE BINDINGS ─────

All bindings injected via platform.env at runtime. Code never
hardcodes account IDs.

  DB              Cloudflare D1 — SQLite at the edge, sub-10ms
                  reads worldwide. Schema managed by Drizzle
                  ORM. 11 migrations to date, applied by the
                  deploy pipeline before the Worker goes live.

  MEDIA_BUCKET    Cloudflare R2 — S3-compatible object storage
                  for uploaded media. Public reads proxied via
                  /api/media/[id] so we can enforce access
                  control if needed.

  CONTENT_CACHE   Cloudflare KV — eventually-consistent
                  key-value cache for computed lookups.

Local development (`pnpm wrangler:dev`) spins up local
simulators for all three. Production IDs stay dormant until
you deploy.

Config layers (kept explicit — see docs/DEPLOYMENT.md):

  Bindings       →  wrangler.toml [[d1_databases]] etc.
  Plain vars     →  wrangler.toml [vars]
  Cf secrets     →  wrangler secret put
  GH Actions     →  GitHub repo/org Secrets


── ContentProvider ABSTRACTION ─────────────

The single cross-cutting seam. Every feature (articles, pages,
forms, newsletter, comments, webhooks, API keys) goes through
this one interface.

  Interface       $lib/server/content/types.ts
  Implementation  D1ContentProvider (providers/d1.ts)

Graph-analysis footprint: 106 edges from this interface into
the rest of the code — the biggest cross-community bridge in
the codebase. That's not an accident; it's the point. Every
feature is composable because they all speak this vocabulary.

Why: keeps tests fast (drop-in mocks), and lets future
backends (Postgres, Turso, tests-only in-memory) slot in
without rewriting call sites.


── AUTH ────────────────────────────────────

Better Auth with D1-backed sessions.

  Method:  Email + password (OAuth deferred to v2.x backlog)
  Roles:   super_admin > admin > editor > author
  Sessions stored in D1 with configurable TTL.

First sign-up flow:
  → creates the account
  → auto-promotes to super_admin
  → then locks signup — returns 403 for every subsequent
    signup attempt.

Additional users come in via time-limited token invitations
(v1.3). Invitations are one-shot, atomically consumed via a
WHERE clause guard so a race between two browsers leaves
exactly one winner.

Centralized permission helpers keep authorization one function
call away everywhere:

  hasRole              — general role check
  canPublish           — editor+
  canManageTaxonomy    — editor+ (categories, tags, pages,
                         forms, comments, navigation, blocks)
  canManageUser        — admin+ with self-guard and last-
                         super-admin protection
  canDeleteArticle     — author owns; editor+ any
  canManageSettings    — admin+


── SEARCH — FTS5 ───────────────────────────

SQLite FTS5 external-content virtual table over
article_localizations.

  Tokenizer:  unicode61 remove_diacritics 2
              (Thai-friendly — the default 'simple' tokenizer
              is ASCII-only)
  Triggers:   AFTER INSERT / UPDATE / DELETE keep index in
              sync automatically. Application code never
              touches the FTS layer.
  Recovery:   `INSERT INTO articles_fts(articles_fts)
               VALUES('rebuild')` — one statement rebuilds
              the entire index from the source of truth if
              anything drifts.

Both public /blog?q= and CMS list share the same index.
Query handling:
  – Default → quoted phrase match (safe for user input)
  – Advanced → passes through FTS5 boolean syntax (AND, OR,
    NOT, NEAR, quotes, parens, wildcards) when detected


── SEO SURFACE ─────────────────────────────

One <Seo> component in (www)/+layout.svelte reads a per-page
PageSeo record via $app/state and emits the entire on-page
SEO surface in one mount.

  – <title>, <meta description>, <link canonical>
  – Open Graph:
      og:title, og:description, og:type,
      og:locale, og:url, og:image, og:site_name,
      article:published_time, article:modified_time
  – Twitter Card (summary or summary_large_image)
  – <link rel="alternate" hreflang=…> per locale, with
    x-default pointing at EN
  – Article + WebSite + SearchAction JSON-LD as separate
    <script type="application/ld+json"> tags
  – RSS auto-discovery <link>

Plus:
  /sitemap.xml            — sitemap index
  /sitemap-{locale}.xml   — per-locale, includes pages +
                            articles + hreflang siblings
  /robots.txt             — per-env (prod allows /, staging
                            emits Disallow: /)
  /feed-{locale}.xml      — RSS 2.0 with content:encoded


── ANALYTICS — v1.8 ────────────────────────

Aggregated counter, not per-request logs. Privacy-by-design.

  Table:    page_views(date, path, kind, ref_id, count)
  Method:   SQLite UPSERT — one row per (date, path), atomic
            count increment via ON CONFLICT DO UPDATE
  Gate:     consent.analytics from the cookie banner
  Stored:   ZERO IP addresses, ZERO user agents, ZERO
            fingerprints

Search log table: term (lowercased) + noResults flag + date
only. Enables the content-gap tile ("searches that returned
nothing").

Dashboard shows:
  – Top articles (30 days)
  – Top search terms (30 days)
  – Searches with no results
  – Per-article 30-day sparkline

Optional third-party layer: Cloudflare Web Analytics beacon.
Loads only when the operator sets a site token AND the
visitor consented to analytics.


── PERFORMANCE & TRUST — v1.9 ──────────────

  Responsive images    /cdn-cgi/image/width=W,format=auto,
                       quality=85<src> — Cloudflare Images
                       serves resized WebP/AVIF; falls back
                       to raw R2 URL if the zone doesn't
                       have Images enabled.

  Cache-Control        Per-route defaults set in cacheHook.
                       /cms/* + auth + consent → no-store.
                       /api/media/* → 1d browser + 7d SWR
                       (R2 blobs are immutable per id).
                       /blog/[slug] → 2min browser + 10min
                       edge + 1d SWR.
                       Everything else → 1min browser + 5min
                       edge + 1d SWR.

  Branded 404 / 500    (www)/+error.svelte with paypers
                       visual language. Search box on 404
                       (posts to /blog?q= → FTS). noindex
                       so error pages never get crawled.

  Health endpoint      /api/health returns
                       { ok, timestamp,
                         bindings: { d1, r2, kv } }
                       with per-binding latency. Always 200
                       when platform is up; 503 only when
                       the wrangler runtime itself is
                       missing.


── ENGAGEMENT & GROWTH — v2.0 ──────────────

FORMS (v2.0a)
  POST /api/forms/[key]
  Defenses:  honeypot (_hp field, expected empty)
             + per-IP-hash rate limit (3 / minute)
  IP:        stored as 16-char truncated SHA-256, never raw
  Storage:   form_submissions table with status enum
             (new / read / spam / archived)
  CMS:       /cms/forms — build fields (text / email /
             textarea / checkbox), embedded submissions inbox

NEWSLETTER (v2.0b — fully optional)
  Default:   single-opt-in when no email provider configured
             (subscribers immediately confirmed)
  With Resend: double-opt-in — token-based confirmation, one-
             click unsubscribe from any email
  Digest:    admin can send a weekly digest of published
             articles per locale
  Endpoints: POST /api/newsletter/subscribe,
             GET /api/newsletter/confirm?token=,
             GET /api/newsletter/unsubscribe?token=

COMMENTS (v2.0c)
  Dual-toggle:
    – site-wide commentsEnabled setting (default OFF)
    – per-article commentsMode: inherit | on | off
  commentsAllowedForArticle() is the truth table both the
  public form and the POST endpoint consult.
  Defenses:  honeypot + IP-hash rate limit (same as forms)
  Moderation: /cms/comments with status tabs
              (pending / approved / spam / archived),
              masked-email display, mailto reply, delete.

WEBHOOKS (v2.0d)
  Events:    article.publish, article.unpublish,
             article.delete, comment.approve,
             form.submit, subscriber.confirm
  Signing:   HMAC-SHA256, header X-Khaopad-Signature
             (sha256=<hex> format)
  Retry:     3 inline attempts with exponential backoff
             (250ms → 1500ms). Every attempt (success or
             fail) logged to webhook_deliveries with
             response status, excerpt, duration.
  CMS:       /cms/webhooks (admin+ only) with the delivery
             log per hook.

PUBLIC REST API (v2.0d)
  Endpoints: /api/public/articles
             /api/public/articles/[slug]
             /api/public/categories
             /api/public/tags
             /api/public/pages
  Auth:      Bearer <token>. Tokens start with kp_live_...
             for GitHub secret-scanning + operator
             visibility.
  Storage:   SHA-256 hash at rest — the raw key is shown
             ONCE at create time and cannot be recovered.
             12-char prefix stored for CMS list display.
  Scopes:    articles:read, categories:read, tags:read,
             pages:read, *:read (grow-friendly — new scopes
             don't need a migration)
  Revoke:    /cms/api-keys → revoke. Propagates via D1
             read-replica within a few seconds.


── CI / CD ─────────────────────────────────

GitHub Actions pipeline in .github/workflows/deploy.yml.

  push to main       → auto-deploy to STAGING
  tag v*.*.*         → auto-deploy to PRODUCTION
  workflow_dispatch  → manual deploy to chosen env

Four-stage gate:  gate → resolve-env → deploy → smoke-test

Per-environment bindings — staging and production each get
their own D1 database, R2 bucket, KV namespace. Nothing
shared across environments.

Migrations apply BEFORE the Worker goes live. Rollback on
migration failure. Smoke test curls the public URL up to
6× (10s backoff) after deploy and treats 2xx/3xx/503 as
healthy.


── AUDIT + OBSERVABILITY ───────────────────

Every CMS action writes an audit_log row:

  article.{create,update,publish,unpublish,delete}
  category.*, tag.*, media.delete
  user.{role_change,delete}
  invitation.{create,accept,revoke}
  form.{create,update,delete,submit}
  newsletter.{subscribe,confirm,unsubscribe,delete,
              digest_sent}
  comment.{create,approve,spam,archive,delete}
  settings.update

Viewer at /cms/audit (admin+). Paginated, filterable by
actor and action. Left-joins users table so deleted-user
rows still render gracefully.

/api/health for uptime monitors. Cloudflare Web Analytics
optional for referrer / device / country breakdowns.

 3.  COMPETITIVE POSITIONING
================================================================

VS. WordPress
  – WordPress: PHP monolith, plugin ecosystem, expensive to
    keep secure and fast. Great if you already have a
    WordPress admin team.
  – Khao Pad: TypeScript-first, edge-native, no plugin
    ecosystem to manage. Better fit for teams already on
    Cloudflare.

VS. Ghost
  – Ghost: purpose-built for publications, excellent editor.
    Node-based hosting, not edge-native.
  – Khao Pad: comparable feature set, deploys on Cloudflare
    free tier, includes forms/webhooks/REST API that Ghost
    charges extra for.

VS. Sanity / Contentful (headless)
  – Sanity/Contentful: hosted, per-seat pricing, powerful
    schema editors, needs a separate frontend build.
  – Khao Pad: self-hosted, no per-seat cost, comes with the
    frontend already built. Trade schema flexibility for
    simplicity.

VS. Strapi / Directus (self-hosted headless)
  – Strapi/Directus: mature, plugin marketplaces, Node.js
    server required.
  – Khao Pad: edge-native from day 1, no separate compute
    layer, i18n and SEO baked in.

VS. Astro + a custom CMS
  – Astro: excellent static-site builder. Great for pure
    marketing pages.
  – Khao Pad: pairs a comparable public site with a real
    admin panel + real DB — no build step to trigger every
    time an editor updates copy.

VS. Roll-your-own on Cloudflare
  – Every dev team can build this from scratch on Cloudflare.
    Nobody wants to. That's the Khao Pad pitch: skip the
    30-primitives that everyone rebuilds and get straight
    to your business logic.

 4.  IDEAL CUSTOMER PROFILE + USE CASES
================================================================

WHO IT'S FOR
  – Small teams (2–20) that need a real website but not a
    real hosting budget
  – Publications, blogs, editorial sites, agencies
  – Multilingual sites where locales are first-class
  – Non-ecommerce sites (Khao Pad doesn't try to be Shopify)
  – Teams already committed to the Cloudflare stack

WHO IT'S NOT FOR (be honest)
  – Ecommerce (use Shopify)
  – Sites that need a WYSIWYG page builder like Wix
  – Teams that must run their own hardware
  – Sites that need real-time collaborative editing (v2.x
    backlog, not shipped)

USE CASE 1 — Publication / editorial site
  Small newsroom, 3 editors, publishes 5–10 articles/week
  in English + Thai. Needs SEO, comments, newsletter,
  search. Runs on Cloudflare free tier.

USE CASE 2 — Agency template
  Agency forks Khao Pad once. Reskins per client. Ships 4–8
  client sites on the same platform. Syncs security fixes
  from upstream. Codustry uses this pattern internally.

USE CASE 3 — SaaS company blog + docs site
  SaaS company wants a marketing site + blog + docs, all
  with search, all bilingual. Doesn't want to run Ghost or
  pay Contentful. Runs Khao Pad on Cloudflare, integrates
  with their product via public REST API.

USE CASE 4 — Non-profit / NGO site
  Non-profit needs a bilingual site with forms (donations,
  volunteer signup), newsletter, and event pages. Needs
  free hosting. Runs Khao Pad on Cloudflare free tier
  indefinitely.

USE CASE 5 — Personal site / portfolio with real content
  Solo developer or writer who wants blog + newsletter +
  comments + SEO without paying for Ghost. Runs Khao Pad,
  deploys via GitHub Actions, updates via git.
